# 37 — A BGP gateway for the transit VPC

> `portico-edge` in this write-up is a router VM built by hand to stand
> for the MSP's router. It is the ancestor of the edge router Portico
> builds since 0.3.0 (prefix-routing design 4.3): the same FRR peering
> with the BGP gateway, now from the release's image with cloud-init and
> no login, and the gateway and the session built by Portico.

## Question

The install guide lets the MSP's router learn the routed prefix "static,
or through a BGP gateway". Nutanix's documented path for externally
routable prefixes is the second one (Flow Virtual Networking Guide 7.6,
"BGP gateways"): a Network Gateway VM on the VLAN runs BGP for the VPC and
advertises its externally routable prefixes to the router, next hop the
VPC's external address, so the router needs no static route and follows
the prefixes as they change. Can it be built on pc.7.6 through the v4
API, what does it take, and does the router (here `portico-edge`, FRR)
actually receive the prefix?

## Measured on

- Prism Central: pc.7.6.0.6 on NTNX-01 (`10.23.210.175`), AOS 7.6, Flow
  Virtual Networking in the Integrated mode; Network Gateway image
  `7.6.9ede470.20260715`, downloaded by Prism Central itself
- Router: `portico-edge` (`10.23.210.194`, Rocky 9, FRR 8.5), the router
  of write-up 35 in front of the transit VPC `portico-transit`
  (`10.23.210.200`, routed prefix `100.96.0.0/24`)
- Date: 2026-10-31 and 2026-11-01
- By: Claude; Marco pointed out the project the UI asks for

## Method

1. FRR on the router: `router bgp 65020`, router id `10.23.210.194`,
   `no bgp ebgp-requires-policy`, neighbour `10.23.210.195 remote-as
   65010` with `soft-reconfiguration inbound`; `bgpd` enabled.
   `lab/network/edge-router.sh` now writes it with cloud-init.
2. `lab/network/bgp-gateway.sh create`: `POST
   /api/networking/v4.4/config/gateways` twice. The remote gateway stands
   for the router (`services` of type
   `networking.v4.config.RemoteNetworkServices`, `remoteBgpService`
   address `.194`, ASN 65020). The local gateway is the Network Gateway VM
   (`deployment` on cluster NTNX-01 with one interface on the VLAN subnet
   `MGMT`, `10.23.210.195/24`, default gateway `.254`; `services` of type
   `networking.v4.config.LocalNetworkServices` with `localBgpService` ASN
   65010 and `vpcReference` the transit VPC, `serviceAddresses` `.195`).
   Both calls answer 201 with a task.
3. `lab/network/bgp-gateway.sh session`: `POST .../bgp-sessions` with the
   two gateway references, the local interface address and
   `shouldAdvertiseAllExternallyRoutablePrefixes: true`.
4. On the router: `vtysh -c 'show bgp summary'`, `show ip bgp`, `ip
   route`; then the static route removed and the kernel route read again.
   In Prism Central: `GET .../bgp-sessions/{extId}/bgp-routes`.

## Result

- MEASURED: the remote gateway is created in about one second and is
  inert (no VM, no status).
- MEASURED: the local gateway's create **fails without a project**. The
  body of 2026-10-31 carried no `projectExtId`; the API accepted it, the
  workflow registered the gateway image (`portico-transit-bgp`, 10 GiB,
  task `kImageCreate` succeeded at 08:29:09) and failed two seconds
  earlier at reading it back: `Failed to Create Network Gateway due to -
  Image create failed with: {'state': 'ERROR', 'kind': 'image',
  'message_list': [{'reason': 'ENTITY_READ_ERROR', 'message': 'image :
  3664e044-… could not be read.'}], 'code': 404}`. No VM was created. The
  UI makes Project mandatory on the same form. With `projectExtId` set to
  the system project `_internal`
  (`00000000-0000-0000-0000-000000000000`, the project that owns the
  transit VPC, the VLAN subnet and the remote gateway) the same body
  succeeds: task `kVpnGatewayCreate` 04:48:02 to about 04:50, VM
  `portico-transit-bgp` (2 vCPU, 4 GiB, 10 GiB disk) created at 04:48:12
  and powered on, image found in the image service. The 404 of the first
  attempt is read as the project-scoped read of Projects 2.0 missing an
  image registered with no project; the CVM reset of 08:38 that day came
  nine minutes later and is not the cause.
- MEASURED: the gateway reports `status.state: DOWN, "Service nginx is
  down"` for about a minute after the VM is on, then `UP` with
  `installedSoftwareVersion 7.6.9ede470.20260715`. A session create during
  that minute is refused: `NETWORKING-10057 … Unable to determine version
  of gateway portico-transit-bgp. Please ensure the gateway appliance is
  up and reachable and retry`. The script now waits for `UP`.
- MEASURED: the session `portico-transit-to-edge` is created in a few
  seconds and reports `UP, "bgp session is up"`. On the router FRR shows
  the neighbour `10.23.210.195`, AS 65010, Established, 1 prefix
  received: `100.96.0.0/24` next hop `10.23.210.200`, path `65010 i`.
  Prism Central lists the same route for the session.
- MEASURED: with the static route in place the kernel keeps it (zebra
  sees a kernel route of distance 0 and does not install the BGP one).
  With the static route removed, zebra installs `100.96.0.0/24 via
  10.23.210.200 proto bgp metric 20` at once; the data path is the same
  next hop, so nothing changes for the tenants' traffic. The static route
  was put back as the fallback for the lab.
- MEASURED: Prism Central keeps the downloaded gateway image in the image
  service under the gateway's name (`portico-transit-bgp`, 10 GiB); a
  second create reuses it.

## Implications for the design

- What is real and what stands in: the Nutanix side (gateway VM in the
  system project, BGP service for the transit VPC, remote gateway,
  session) is what an MSP configures in production, to the parameter.
  `portico-edge` stands in for the site's router, which the lab cannot
  configure: a production router is the VLAN's gateway itself, routes
  the prefix natively and NATs nothing here, and has its own
  redundancy. The edge's NAT of the routed prefix and its role as the
  external subnet's gateway are lab artefacts.
- The install guide's "static, or through a BGP gateway" holds, and the
  BGP gateway is the path to recommend to an MSP: the router learns the
  routed prefix from Prism Central, and a change of prefix or of transit
  address needs no router ticket. The static route stays the simple path
  for a site whose router admin will not peer.
- The gateway's project matters: it is the system project, like the
  transit VPC and the external subnet, never a tenant's. A Networking
  card that one day creates the gateway for the MSP sends
  `projectExtId` of the system project.
- The Networking card could read `GET .../bgp-sessions` and show the
  session's state next to its nine checks when a session exists for the
  transit VPC (backlog).
- Two more VMs per site for an MSP that goes this way (the gateway, plus
  the router it already has); the gateway is 2 vCPU and 4 GiB.

## How to re-measure after an upgrade

```
source lab/env.sh
lab/network/bgp-gateway.sh create     # remote gateway, then the local one
lab/network/bgp-gateway.sh session    # waits for the gateway UP
lab/network/bgp-gateway.sh show       # gateways, session, routes
ssh admin@10.23.210.194 "sudo vtysh -c 'show bgp summary'"
lab/network/bgp-gateway.sh delete     # session, then the two gateways
```
