# Portico 0.1.0

The first installable release of Portico: a virtual appliance that runs
inside a Nutanix cluster and is the single, authenticated entry point
through which a managed service provider's tenants reach Prism Central.
One Go binary fronts Prism Central and Keycloak on two public names, lets
nothing through without a login, creates a tenant in one action and keeps
platform administration on an internal listener.

Portico is an independent project, not affiliated with or supported by
Nutanix. It is provided "as is", without warranty (Apache-2.0). This
release is for trying Portico with real tenants on an MSP's own Prism
Central; read the known limits below before putting it in front of
customers.

## What is in it

- **Public path.** No Portico session, no request to Prism Central: the
  public path fails closed, also with the identity provider down. Every
  `Authorization` header and every local-login path of pc.7.6 is
  refused, so local Prism Central accounts never authenticate from
  outside. Direct exposure on 443 or a Cloudflare tunnel, same rules
  (write-ups 06, 09, 10).
- **Identity.** Keycloak 26: OIDC for Portico, SAML for Prism Central,
  one login for the tenant user (write-ups 04, 12, 13).
- **Sites.** Several Prism Centrals behind one portal name, shown to
  tenants by a code such as `AZ-IT-MI1`; a site is added in one step
  from its address and a one-time account, which Portico does not keep.
  Maintenance, the list of connected users and their disconnection
  (write-ups 21, 24 to 26).
- **Tenant arrival.** One action places a tenant on its sites: a
  Projects 2.0 project, a SAML group and a project-scoped role on each,
  one Keycloak group, then a visibility check. Disable, enable, delete;
  users with a one-time temporary password (write-ups 11, 25).
- **Branding.** The MSP's name, claim, colours, logo and tab icon on the
  Keycloak login page, the portal's pages and its error pages
  (write-ups 17, 22, 23).
- **Admin path.** A web UI and a JSON API on port 8443 only, a
  break-glass account with a factory password changed at the first
  login, settings sealed with a master key that never leaves the
  appliance (write-ups 14 to 16, 18).
- **Appliance image.** Rocky Linux 9 with the CIS Level 1 Server
  baseline (OpenSCAP report attached), SELinux enforcing, a console
  wizard on tty1, `cloudflared` for tunnel mode; an OpenTofu module
  creates the VM in Prism Central (write-ups 19, 29).

## Requirements

- Prism Central pc.7.6 or later (Projects 2.0), one per site.
- Port 9440 of every Prism Central reachable from the appliance and
  the management network only.
- Two public names, the portal and the identity provider, and one
  certificate for both (or a Cloudflare tunnel).
- Internet access from the appliance at its first boot: PostgreSQL and
  Keycloak are pulled from `docker.io` and `quay.io`.
- An AHV cluster with 2 vCPU, 6 GiB of memory and 40 GiB of disk for
  the appliance, or a Rocky Linux 9 host of your own.

The install guide is [docs/install.md](../install.md).

Each file has a `.sha256` beside it. Download both into one directory
and run `sha256sum -c <file>.sha256` there.

## Upgrading from a development build

Take a snapshot of the VM in Prism Central first. Then, on the
appliance, unpack `install-0.1.0.tar.gz` and run
`./deploy/install.sh --release 0.1.0` as root. The installer stops
Portico, copies the store and the master key to
`/var/lib/portico/backup-<old version>-<time>/`, replaces the binary and
its files and starts again; open sessions end.

The settings now name the portal `portal_host`. 0.1.0 still reads the
old name, `prism_host`, but writes the new one at the first save. A
development build from before the rename (before 2026-10-25) does not
read `portal_host`. To go back below the rename, restore the snapshot,
or the backup the upgrade took. Do not install the old binary over the
new store.

## Known limits

- **The first boot needs the Internet.** The image carries no container
  image, so an appliance without egress to `docker.io` and `quay.io`
  never gets its identity provider. On a slow link Keycloak is up about
  a minute after the network (write-up 29).
- **Backup is a snapshot of the VM.** Keycloak's database (the realm,
  its clients, every tenant user) lives in a container volume, outside
  `/var/lib/portico`. A snapshot or a protection policy in Prism Central
  saves both and keeps the master key inside the appliance. There is no
  application-level export, and no path that moves an appliance's
  state onto a new image.
- **The public names cannot change after setup.** The setup writes them
  into Keycloak and into each site's identity provider, and Apply does
  not carry a new name there.
- **Tunnel mode is not measured with a real Cloudflare tunnel.**
- **Tenant users are Keycloak users.** There is no brokering to a
  customer's own directory, and access is through the browser only:
  there are no tenant API keys.
- **No adoption of what exists.** Portico does not take over existing
  projects. When Prism Central already holds a SAML identity provider
  with the name Portico would give its own, the site setup refuses and
  says so; it never adopts or overwrites it.
- **Disabling a tenant does not end a Prism Central session already
  open.** Prism Central ends it at its own limits (15 minutes idle, 8
  hours).
- **Prism Central's gateway can fail a tenant step.** A transient `401`
  or `504` fails the step; Retry on the tenant page completes it
  (write-up 28).
- **Disconnect does not count floating IPs or Flow security policies.**
  The service account's role cannot read them, and Prism Central refuses
  to delete a project that still holds one (write-up 25).
- **Every site uses the pc.7.6 API paths.**
- **The pair of two appliances is not measured.** A maintenance flag set
  on one node reaches the other only when that one restarts.

The deferred findings behind these limits are listed in
[docs/backlog.md](../backlog.md).

## Measured on

Prism Central pc.7.6.0.6 on two single-node AHV clusters, Keycloak 26.3,
the appliance built from the image `0.1.0-rc.1`: a fresh appliance from
the image, both sites added in one step, tenants created, disabled,
enabled and deleted, maintenance and disconnection, every local-login
path refused, and two upgrades in place (write-up 29). There was no
production load.
