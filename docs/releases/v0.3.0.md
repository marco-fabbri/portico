# Portico 0.3.0

The routed prefix of a site reaches the MSP's router by eBGP, built by
Portico. Portico behaves as in
[0.2.0](https://github.com/marco-fabbri/portico/blob/v0.3.0/docs/releases/v0.2.0.md)
with the fixes of 0.2.1 and 0.2.2, whose requirements and known limits
still apply, and adds the routing below.

## What changed

- **The eBGP peer is the requirement.** The Networking card's new
  **Routing** section asks for the peer of the site's routed prefix.
  Portico builds a BGP gateway on the external subnet's VLAN (a Network
  Gateway VM in the system project with the BGP service for the transit
  VPC, named `portico-<site>-bgp`), a remote gateway standing for the
  peer and the BGP session between them, which advertises the routed
  prefix with the transit VPC's address as next hop. The static route
  of 0.2.x stays the manual way, and is what a site built before this
  release has until the MSP picks a peer.
- **Your router** as the peer: its address on the VLAN and its ASN; the
  card shows the three lines the router needs and the session's state
  as Prism Central reports it.
- **An edge router built by Portico** as the way out, for a router that
  cannot peer: one free address on the VLAN, and Portico creates a small
  VM (1 vCPU, 1 GiB, 10 GiB) from the release's edge image, peers it
  with the gateway, points the external subnet's gateway at it, and
  shows the one static route the core needs. The edge has no user, no
  password and no SSH; its console shows its state.
- **The peer moves**: from the router to the edge and back, Replace the
  edge with a new release's image, Repair what is missing, Delete the
  edge once the router peers; each is a recorded operation with its
  state on the card.
- **The switch waits for the session.** With a router or an edge as the
  peer, the ready network switch stays off until the BGP session is
  `UP`; the monitor reads the gateway and the session at its pace and
  stores the state, so a session that goes down shows on the card and on
  the setup page's site row. Switching the network off tears the
  peering down once no connection holds a ready network.
- **The service account's rights** cover the gateways, the sessions and
  their routes, the edge's image, VM and category, the external subnet's
  gateway and the cluster; Repair gives them to a site set up before.
- **A second release artefact**, `portico-edge-<version>.qcow2`, with
  its checksum and its OpenSCAP report: Rocky Linux 9 GenericCloud with
  FRR and nftables, the appliance's CIS Level 1 Server profile with the
  same exceptions and the SSH server rules set aside. Portico imports it
  into the site's image service by URL from the release, or finds it by
  name when the MSP uploaded it (a Prism Central without Internet
  access).

## Fixed

- **A new ready network failed on 0.2.2** with `404 portico-<tenant>-ext
  not found` right after Prism Central created the subnet: pc.7.6
  reports the system project `_internal` as the project of a subnet,
  VPC or floating IP created without one, and 0.2.2's read-back took
  only an empty project as "no project". Portico now reads the system
  project as none (write-up 39). A tenant whose network failed that way
  gets it with **Retry network** on its page after the upgrade.

## What you give

For every site whose routed prefix is to be learnt by BGP (install
guide, "The transit VPC, once per site"): one address on the VLAN for
the BGP gateway, outside the external subnet's pool, with the VLAN's
router as its default gateway (the router that forwards the routed
prefix: it is the edge router's default route and the external subnet's
gateway in router mode) and an ASN (65010 proposed); then either
your router's address on that VLAN and its ASN, or one free address for
the edge router (ASN 65020 proposed).

## Known limits

- The edge router is one VM: a replacement (a new release, a repair, a
  change of address) is break-before-make, and the routed prefix is
  unreachable for under two minutes (write-up 39: 38 s to the new VM
  plus its boot), in a window you pick; the static route on the core
  never changes.
- On a router that runs FRR a static route to the routed prefix keeps
  the route learnt by BGP out of the kernel whatever its metric: remove
  the static route once the session is up, and the core's static route
  to the edge router once your router is the peer.
- The BGP gateway's own reference in a session is fixed by Prism
  Central: a move that needs another remote gateway recreates the
  session (the new remote exists before the old session goes).
- A session reports `DOWN` about three and a half minutes after its
  peer goes away (the BGP hold time), and `UP` again a few minutes after
  the peer is back; Portico shows what Prism Central reports and takes
  no action of its own.

## Upgrading from 0.2.x

The upgrade is in place (install guide, "Updating"). A site set up
before keeps its static route and shows `static` as its peer; Repair on
its page gives the service account the new rights, and the Routing
section is where the MSP picks the peer when ready.

## Measured on

Prism Central pc.7.6.0.6, AOS 7.6: the gateway, the session and their
updates (write-up 38), then the acceptance of this release with the
router and the edge as peers, the moves between them and the Repair of
the rights (write-up 39).
