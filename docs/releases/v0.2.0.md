# Portico 0.2.0

The tenant **ready network**. On a site whose MSP switched it on, a
tenant connected to the site gets its own VPC with a `/24` subnet,
outbound access through the MSP's network, and floating IPs that publish
its VMs, without anyone opening Prism Central. It follows the routed
form of the shared transit VPC in Nutanix's NVD-2219: the MSP builds one
transit VPC per site, once; Portico builds and removes each tenant's
part of it. A site without it keeps working as in 0.1.x.

Portico is an independent project, not affiliated with or supported by
Nutanix. It is provided "as is", without warranty (Apache-2.0). The
requirements and known limits of
[0.1.0](https://github.com/marco-fabbri/portico/blob/v0.2.0/docs/releases/v0.1.0.md)
still apply, except where this page says otherwise.

## What is in it

- **The site's Networking card.** It reads what the ready network needs
  from Prism Central each time the page opens: Flow Virtual Networking
  and its controller, Prism Central's gateway, the transit VPC (type,
  no-NAT VLAN external subnet, default route, routed prefix), the
  service account's networking rights, the *Portico Tenant* role, the
  DNS servers and the free `/28`s. The MSP picks
  the transit VPC, gives the DNS servers, confirms the Integrated mode
  and switches it on; the switch stays off until every check passes.
- **The address plan.** Each tenant gets a `/24` from the MSP's address
  pool (`10.100.0.0/16` by default), the same on every site, or a subnet
  exception chosen at creation; a `/28` of the transit VPC's routed
  prefix per tenant and site, skipping the ranges of subnets already in
  the transit VPC; Prism Central gives the VPC its outbound address and
  the floating IPs from the `/28`'s pool, and Portico reads them back.
- **Seven network steps on Connect**, after the connection is active:
  the tenant's overlay external subnet on its `/28`, its sharing with
  the project, the VPC, its default route, the subnet, the floating
  IPs, and a read-back that checks every object belongs to the project.
  The network has a state of its own: a failure shows its reason and
  **Retry network**, and never fails the connection. A tenant connected
  before 0.2.0 gets its network with **Create ready network**.
- **Disconnect in reverse.** Floating IPs, subnet, VPC, the sharing and
  the overlay external subnet are removed before the project; a floating
  IP still associated with a VM refuses the Disconnect and is named.
  Portico's own network objects no longer count as the project's
  contents.
- **Floating IPs per site**, 0 to 12 (1 by default), set by the MSP on
  the tenant's page: Portico creates or deletes unassociated ones to
  match and never deletes one a VM uses.
- **Two roles created by the site setup.** *Portico Networking* and its
  policy give the service account the networking operations; *Portico
  Tenant*, Project Admin without the floating IP operations, is the role
  tenants get in their project, so the allowance holds. A site set up
  before 0.2.0 keeps Project Admin for its tenants until one **Repair**.
- **The watch.** Every five minutes Portico reads what it created by
  stored `extId`; an object a tenant deleted or moved in Prism Central
  turns the network to `failed`, and Retry network creates again what
  is missing. The watch creates and undoes nothing.
- **API.** `POST /api/v1/tenants/{id}/sites/{site}/network` and
  `.../network/retry`, `PUT /api/v1/tenants/{id}/floating-ips`, and the
  `subnet` and `floating_ips` fields of tenant creation
  ([docs/api.md](https://github.com/marco-fabbri/portico/blob/v0.2.0/docs/api.md)).

## Upgrading from 0.1.x

Update as the install guide says. At the first start Portico gives every
existing tenant a `/24` of the address pool, in creation order. The pool
can still change until a ready network uses one of its `/24`s: the
tenants' `/24`s then move into the new one; a tenant's subnet exception
is set on its page until then (ADR 0008). Then, on
each site that will have the ready network: **Repair** once (it creates
the two roles and moves the tenants to *Portico Tenant*), build the
transit VPC if it is not there, and switch the Networking card on.
Existing tenants get their network with Create ready network.

## Known limits

- **The networking policy's filters are wide.** The *Portico
  Networking* policy grants its operations on every subnet, VPC, route
  table and floating IP (`*`): an entity filter narrower than that is not
  measured yet.
- **One transit VPC per site**, and it cannot change while tenants hold
  a `/28` of it. It serves its own cluster: a connection placed on
  another cluster of the site gets a failed network that says so.
- **A subnet exception is checked against the site when the network is
  built.** One that overlaps the site's routed prefix or external subnet
  fails the network; the MSP changes it on the tenant's page.
- **The Integrated mode is confirmed by the MSP.** Prism Central's API
  does not say which mode Flow Virtual Networking runs in; the card
  takes the MSP's word for it.
- **The readiness checks run when the card opens.** The watch reads the
  tenants' objects, not the site's readiness: a site that loses Flow or
  its transit VPC shows it on its card, and new networks fail with the
  reason.
- **Tenants do not manage their project's members.** Prism Central keeps
  `Create_Role_Membership` and `Delete_Role_Membership` for its own
  roles, so *Portico Tenant* has Project Admin's operations without them:
  the MSP adds a tenant's users in Portico, as in 0.1.0.
- **Integrated mode only, IPv4 only, no subnet stretch between sites,
  no VPN.**

The limit of 0.1.0 on floating IPs ("Disconnect does not count floating
IPs") is lifted on sites with the ready network: Portico removes the
ones it created, and names an associated one.

## Measured on

Prism Central pc.7.6.0.6 on two single-node AHV clusters with Flow
Virtual Networking in the Integrated mode, and the transit model of
write-up 34; the acceptance run of the release is write-up 35.
